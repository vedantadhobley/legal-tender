# Reproducible Go build gate — 2026-09-14

Status: accepted. Two clean offline builds and an independent archive-only
rebuild produce the same executable. Full CGO-disabled Go tests, CLI help smoke
checks, four negative checks, success markers and retained checksum checks pass.

## Contract and scope

The [build contract](../go-build.md) pins a Linux/amd64 Go 1.26.5 image, CGO off,
architecture level v1, explicit compiler flags and a clean environment. Release
and Docker Go stages call the same compiler script. The controller rejects image
pin drift in Dockerfile defaults. Production Python images were not rebuilt or
deployed by this gate; their package/runtime reproducibility remains separate.

Each build extracts the same source/module archives into a fresh container with
its own compiler cache. Source paths differ. The second sets conflicting
`GOFLAGS`, CGO, architecture, workspace, user-config and toolchain settings;
the wrapper ignores them. Network access is disabled throughout. The source
snapshot excludes secrets, `.git`, legacy Python and application data.

The source tests retain paths for existing `runtime.Caller` fixtures. They run
with CGO disabled but are not the release executable. Both release binaries pass
the CLI help smoke check and have no ELF dynamic loader. Race tests and real-data
graph/query gates were not rerun for this build-only change.

Negative checks reject an existing output without changing its hash, a wrong
compiler version, absent offline modules and a modified module. Each checks its
specific error. A separate controller retry against the accepted output directory
also fails before overwriting its successful evidence.

## Remaining boundary

This establishes reproducible Go executable bytes for the pinned environment,
not arbitrary toolchains, CPU architectures or older host-built audit binaries.
The compiler image is pinned but not exported by this gate. Docker/Python/OS
runtime closure, extraction tools, complete data dependencies and enforced
retention still belong to the [pre-attribution recovery checkpoint](../design/pre-attribution-review.md).
The complete typed-manifest dependency inventory remains the next recovery step.
