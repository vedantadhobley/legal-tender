# Production Readiness Gaps

**Date**: 2026-05-07
**Scope**: what's missing for a real production deployment of legal-tender, contrasted with what's already in place. The user's plan is `~/workspace/prod/legal-tender/` with GitHub Actions auto-deploying on `main` push and rebuilding the image automatically.

Severity:
- 🔴 **Blocker** — can't deploy to prod without this
- 🟠 **Reliability concern** — works but will hurt at runtime
- 🟡 **Quality of life** — production runs better with this
- 🔵 **Nice-to-have** — defer if needed

## What's already in good shape

- ✅ **Production Dockerfile** (`Dockerfile`) — multi-stage-ish, layer caching, non-root user (`dagster:1000`), source baked in (not bind-mounted)
- ✅ **Production compose** (`docker-compose.yml`) — separate `dagster-webserver` + `dagster-daemon` processes (the right Dagster prod pattern, not just `dagster dev`)
- ✅ **Healthchecks** on all 3 prod services (webserver, postgres, arango) with reasonable intervals/timeouts/start_periods
- ✅ **`restart: unless-stopped`** on all services
- ✅ **Tailscale FQDN redacted** from committed files (we did this earlier in the session)
- ✅ **Per-service Docker networks** (`legal-tender-prod`, plus `luv-prod` for cross-project)
- ✅ **Persistent volumes** named per-environment (no dev/prod cross-contamination on data)
- ✅ **Recent Arango memory tuning** (32 GB block cache, 32 GB query memory, 16 GB write buffers) in both compose files
- ✅ **Existing observability stack** at `~/workspace/monitor/` — Prometheus, Grafana, Loki, Promtail, amd-gpu-exporter, secrets/

The hard work of "make this run reliably in a container" is mostly done. The gaps are at the boundaries: CI/CD, monitoring integration, backup, secret management, deployment automation.

## 🔴 Blockers

### 1. No CI/CD
**Evidence**: `.github/workflows/` doesn't exist.

You described the target: `~/workspace/prod/legal-tender/` auto-pulls `main`, rebuilds image, restarts containers. That doesn't exist yet. Specific deliverables:

- **`.github/workflows/build.yml`**: on push to `main`, build the Docker image, push to GHCR (or local registry on the host)
- **`.github/workflows/test.yml`**: on PR, run lint + (eventually) tests
- **Self-hosted runner OR webhook receiver** on this host that pulls + restarts when GHCR image updates. GitHub Actions runners self-hosted is the cleanest pattern.
- **Image versioning**: tag images with commit SHA + `latest`. Production compose uses `image: legal-tender:latest` — needs a strategy for "latest" floating vs. pinned

### 2. No backup strategy for ArangoDB state
**Evidence**: `dumps/fec/*.jsonl.gz` exists at `~/workspace/data/legal-tender/dumps/` but no automated snapshot/retention.

The dumps act as backup material, but currently:
- They're regenerated by the parse layer (overwriting older versions)
- No off-host copy
- No retention policy
- No restore-from-backup runbook

Production needs:
- **Periodic Arango dump** (separate from the Dagster-managed dumps) — `arangodump` to a versioned snapshot dir
- **Off-site copy** — at minimum copy to another disk or cloud bucket
- **Documented restore procedure** in `docs/operations.md`

### 3. Secret management for production
**Evidence**: `.env` file is gitignored but lives in plaintext on the host. Prod compose has `env_file: - .env`.

For dev, `.env` plaintext is fine. For prod with auto-deploy:
- Where do secrets come from when CI rebuilds the image / restarts containers?
- Options:
  - **sops + age keys** on the host (good fit for self-hosted)
  - **Docker secrets** (built-in but limited)
  - **HashiCorp Vault** (overkill for solo)
  - **Just keep `.env` on the host and never commit** (works but fragile — what if you reprovision the host?)

The neighbor stack at `~/workspace/monitor/secrets/` suggests you may already have a secrets pattern. **Action**: read the monitor stack's secrets handling and adopt the same pattern for legal-tender.

### 4. No resource limits on containers
**Evidence**: no `deploy.resources` or `mem_limit`/`cpus` in either compose file.

Right now Arango can request up to 64 GB (per the recent tuning) but nothing caps it. If something else on the host claims memory, the kernel decides who gets OOM-killed. Setting explicit limits gives the orchestrator a budget to enforce:

```yaml
arangodb:
  deploy:
    resources:
      limits:
        memory: 64G
      reservations:
        memory: 32G
```

Worth doing for arangodb, postgres, and webserver in prod.

## 🟠 Reliability concerns

### 5. No Prometheus metrics from the pipeline
**Evidence**: no `prometheus_client` in `requirements.txt`, no `/metrics` endpoint in the Dagster code, no scrape config in monitor stack pointing at legal-tender.

The monitor stack at `~/workspace/monitor/` has Prometheus + Grafana ready. We're not feeding it anything from legal-tender. Useful metrics to expose:

- Per-asset run duration + success/failure counter
- Per-cycle row counts for FEC parsers (so you'd see indiv 2026 growing)
- Per-channel funding totals (sanity check — drift in unaccounted % is interesting)
- Wikidata cache hit/miss rate
- Arango query latency p50/p95

Dagster has built-in Prometheus integration via `dagster-prometheus` (if it's still maintained) or Dagster's own metrics. **Phase 4 candidate**.

### 6. Logs not shipped to Loki
**Evidence**: `~/workspace/monitor/promtail/` exists but legal-tender containers' logs go only to docker's default JSON file driver.

Promtail can scrape Docker logs by container label. Adding `logging:` config or labels to the prod compose services lets the existing Loki+Grafana stack ingest them. Then you have queryable logs for "show me all wikidata warnings in the last 24 hours" — which would have caught yesterday's runaway sooner.

### 7. The schedule is set to `STOPPED` by default
**File**: `src/schedules/__init__.py:13` — `default_status=DefaultScheduleStatus.STOPPED`

For dev, this is correct (you don't want a sync running unattended). For prod, you want it RUNNING so the weekly Sunday refresh actually happens. Phase 4 should add a way to differentiate: maybe an env var `DAGSTER_SCHEDULES_ENABLED=true` that's set in prod compose only.

### 8. The `fec_pipeline_job` runs `AssetSelection.all()`
**File**: `src/jobs/asset_jobs.py`

In prod, this means the schedule materializes EVERY asset Sunday 2am — including the broken `wikidata_corporate_resolution` (which we just spent 14 hours on) and the broken `spent_on` (int/float bug). After Phase 3 fixes those, it's fine, but Phase 3 should verify before the schedule is enabled in prod.

### 9. No rollback story
**Evidence**: production compose pulls `image: legal-tender:latest`. No way to "revert to last known good" if a deploy breaks things.

Options:
- Keep last 3 image tags pinned, prod points at a SHA, rollback = repoint
- Manual `docker compose pull <prev-sha>` + `up -d`
- GitHub Actions workflow that builds + tags but a human triggers the prod swap

For solo + self-hosted, keeping the last 3 SHA tags around and a `make prod-rollback PREV=<sha>` target is probably enough.

## 🟡 Quality of life

### 10. No `docs/operations.md`
A single doc for the kind of "how do I…" knowledge that ends up living in heads or chat scrollback:

- How to run a manual sync for one cycle
- How to restore Arango from dump
- How to inspect a stuck Dagster run
- How to drain + redeploy
- How to recover from "wikidata cache corrupted"
- Common errors and their meanings

Phase 1 stub, Phase 3+ fills in.

### 11. No `Makefile` or `justfile`
Common ops commands are scattered across README, PIPELINE.md, and Bash scrollback. A `justfile`:

```
dev-up:
    docker compose -f docker-compose.dev.yml up -d
prod-up:
    docker compose -f docker-compose.yml up -d
sync-2026:
    docker exec legal-tender-dev-webserver dagster asset materialize \
      --select data_sync --config-json '{"ops":{"data_sync":{"config":{"cycles":["2026"]}}}}' \
      -f /workspace/src/__init__.py
arango-shell:
    docker exec -it legal-tender-dev-arango arangosh --server.password ltpass
logs:
    docker compose -f docker-compose.dev.yml logs -f
```

Phase 4 candidate.

### 12. Versioning
**Evidence**: no semver tags on git, no CHANGELOG.md.

For solo prod use this is OK to defer, but eventually:
- `git tag v0.X.Y` cut on each meaningful release
- `CHANGELOG.md` populated from `docs/decisions.md` (see Phase 1 plan rename)
- Prod images tagged with the semver

### 13. License + contribution
README says "MIT" at the bottom. No `LICENSE` file at root. Not strictly a prod blocker but if anyone else ever touches this project, it matters.

## 🔵 Nice-to-have

### 14. Test infrastructure
Already covered in `code-quality-findings.md` Section 9. Restating because Phase 4 should at minimum:
- Set up `tests/` directory + `pytest.ini`
- Add a few smoke tests (e.g., parser correctness on tiny fixture FEC files)
- Wire CI to run them on PR

### 15. Performance benchmarking
We just sat through a 50-min indiv parse. Were the new Arango memory settings actually helping? Hard to say without before/after numbers. A simple harness:
- Reset the relevant collection to empty
- Run the asset, capture wall-clock time
- Repeat after a config change, compare

**Phase 4** if you ever want to tune further. For now, the tuning was qualitatively-correct (block cache + write buffers), and quantitative validation isn't urgent.

### 16. Public deploy / SSO
If this ever becomes a service rather than personal use:
- Reverse proxy in front (Caddy/Traefik)
- TLS certs (Let's Encrypt)
- Auth (Tailscale Funnel + Tailscale serve, or actual auth provider)
- Rate limits

Way out of scope right now. Park for "if and when."

## What I'd ship as v1 production

**Phase 4 minimum to call it "production":**

1. CI build pipeline (item 1)
2. Backup retention for Arango (item 2)
3. Secret management consistent with monitor stack (item 3)
4. Resource limits in prod compose (item 4)
5. Prometheus + Loki integration (items 5, 6) — even if minimal
6. Schedule enabled correctly in prod (item 7)
7. `docs/operations.md` runbook (item 10)
8. After Phase 3 fixes: re-enable `fec_pipeline_job` with confidence (item 8)

That's a real production deploy. Items 9 (rollback), 11 (justfile), 12 (versioning), 13 (license), 14 (tests), 15 (perf benches), 16 (public deploy) are improvements you can sequence afterward.
